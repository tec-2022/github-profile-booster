## v2 workflow: diagnose → compare → position → publish

GitHub Profile Booster is no longer just a collection of README templates and badges. The core product is now a browser-based **career/profile intelligence toolkit** built around public evidence.

```text
Career Signal Map
→ Compare two career goals
→ Goal-Aware Optimizer
→ Generate / edit README
→ Publish
→ Re-audit
→ Share the result
```

The goal is simple: help a visitor understand **what your public GitHub currently proves, what direction it supports best, and which evidence should be featured for the direction you actually want.**

---

## 🧭 1. Career Signal Map

**Question:** _What does my GitHub currently say I am?_  

The Career Signal Map compares your original public repositories across several directions at once:

- Frontend
- Backend
- Full Stack
- Data / AI
- Open Source
- Academic / Research

It ranks the visible evidence and shows which repositories contribute most strongly to your top directions.

Results are **shareable by URL** and can be exported as a **1200×630 PNG signal card**.

**[Open Career Signal Map →](https://tec-2022.github.io/github-profile-booster/career-map.html)**

---

## ⚖️ 2. Career Goal Comparison

**Question:** _Backend or Full Stack? Frontend or Data/AI? Which one does my current GitHub support better?_  

The comparison tool evaluates the **same public profile against two different career goals side by side**.

It shows:

1. A score for each selected direction.
2. The gap between them.
3. Five evidence dimensions for each goal.
4. The strongest repositories for each direction.
5. Repository overlap that can transfer between both goals.
6. A practical **bridge plan** toward the second selected goal.
7. A reproducible share URL.
8. A downloadable comparison card.

**[Compare two career goals →](https://tec-2022.github.io/github-profile-booster/compare-goals.html)**

Example maintainer demo: **[Backend vs Full Stack for @tec-2022](https://tec-2022.github.io/github-profile-booster/compare-goals.html?user=tec-2022&a=backend&b=fullstack)**

> Comparison scores are presentation heuristics. They do not measure programming ability or probability of getting hired.

## 🎯 3. Goal-Aware Profile Optimizer

**Question:** _I know where I want to go. Which public work should represent me?_  

Choose a target such as Internship/Junior, Frontend, Backend, Full Stack, Data/AI, Open Source or Academic/Research.

The optimizer then:

1. **Scores five dimensions** — clarity, proof of work, freshness, goal relevance and credibility.
2. **Ranks the strongest repositories for that specific goal** instead of blindly choosing the most-starred repos.
3. Checks whether selected repositories are documented and current.
4. Prioritizes the highest-impact profile fixes.
5. Generates an evidence-based profile README draft using public work it actually found.
6. Creates a reproducible result URL.
7. Exports a social result card.

Repeated API requests are cached locally for a short period to reduce unnecessary calls.

**[Open Goal-Aware Optimizer →](https://tec-2022.github.io/github-profile-booster/optimizer.html)**

## Why this is different

Many excellent GitHub profile tools are optimized for **adding things**: badges, trophies, streaks, widgets, stats cards and animated sections.

GitHub Profile Booster is deliberately built around **evidence, positioning and direction**.

| Typical profile tool | GitHub Profile Booster |
| --- | --- |
| “Which widgets do you want?” | “What does your GitHub currently prove?” |
| One generic profile | Multiple career lenses |
| Manually choose projects | Rank existing public repos for the selected goal |
| One target at a time | Compare two career goals side by side |
| Generates prettier Markdown | Generates a narrative grounded in public evidence |
| More visual elements = more complete | Proof, freshness, relevance and clarity matter more |
| Static result | Shareable URL + downloadable result card |
| Generic checklist | Prioritized fixes + bridge plan |

The objective is not to create the loudest README. It is to create one a visitor can **understand and verify quickly**.

---

## Five evidence dimensions

### Clarity
Can a visitor understand who you are and what you focus on quickly?

### Proof of work
Do the strongest claims lead to public repositories, demos or documented artifacts?

### Freshness
Does the visible work still reflect what you can do now?

### Goal relevance
Would the featured projects make sense for the direction you selected?

### Credibility
Are the visible repositories documented, maintained and supported by public evidence?

## Quality and safety

Every push and pull request runs GitHub Actions checks that validate:

- required public pages exist;
- inline JavaScript parses successfully;
- basic page metadata is present;
- relative links resolve;
- the README references the flagship tools;
- the comparison and sharing controls remain present.

Public pages escape user-controlled repository text before inserting it into generated HTML views.

The browser tools work only with public GitHub information. Never publish credentials, private database URLs, client data, personal secrets or proprietary code.
